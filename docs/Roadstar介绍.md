# Roadstar · 引路星

今天跟大家分享一个我自己做的 Claude Code 技能，叫 Roadstar，中文名引路星。它从 9 月 24 号开始做，最早叫 roundtable，就是圆桌的意思，到现在改到 1.4 版，前后两个多星期，中间拿它真正干过七八个项目，最重的一次是两天派了二十来条 Codex 的线，发了五个 TestFlight 版本。我个人来讲用下来是非常满意的，因为它解决了我三个非常大的问题。

## 为什么要做它

首先第一个是额度的问题。我手里面 Claude 和 GPT 两边都有订阅，但是我个人感觉 GPT 的能力要比 Claude 差一些，所以以前基本都在用 Claude，而 Claude 的周额度又不是特别的够用，经常用到一半就撞上限了；GPT 那边的订阅钱照样交，额度却大部分闲着，这个多少有一点浪费。但是 Claude 有一个非常强的地方，就是整理和指挥的能力非常的好，所以我就想，能不能让 Claude 来当总调度，想方案、拆活、派活、验收，真正写代码的活全部交给 GPT 的 Codex 去干，这样两边的订阅就都用上了。这就是做这个东西的初衷。

另外一个是一件事一次想不完的问题。我用 AI 时间长了之后发现一个规律，同一件事，让它想完了，再跟它说一句「再想想」，它总能再想出几个新的点来，再让它想，还能再想出来。所以一个方案不能只过一遍，得来回迭代三四次。而且有很多问题 Claude 自己看不出来，Codex 一看就能看出来，反过来也一样，两个模型的盲区不重合。所以最早做它，就是想让这两个模型坐在一张圆桌上，围着同一份方案互相挑毛病，按我们当时的判断，两到三版就基本能迭代到满意。

再有一个是派活和验收的问题。以前一个大项目，要么全压在一个模型身上，要么我自己想哪块给谁，非常的累。现在从拆活、选模型、派出去到收回来验收这一整套都由 Claude 管，我只在几个关键的地方拍板，而且每一步都记在文件里，回头都能翻。

## 三种用法

在项目里对 Claude 说一句「用 skill」，它会先看现场是什么情况，自己判断走哪一种，然后开场报一行出来就跑。我也可以直接点名走哪种。

第一种是探讨，对应全新的项目，或者我只有一个想法的时候。Claude 先写方案，Codex 用最强的型号来审，审出来的每一条都要带证据，比如哪个文件哪一行，或者一段命令的输出，然后 Claude 一条一条处置，接受的就改方案，不接受的要写理由，拿不准的标出来问我。默认三轮，规模大的四轮，两边都没有新问题了它会提前停。谈完给我一份大白话的纪要，里面是方案、讨论改了什么、还要我定的事，和一张拆分表，我说开工才开始干。要动数据结构、难回滚、对外发布之前的大改，也走这一种，因为做错了返工的代价太大。

第二种是复盘，对应项目已经有了，我想知道哪里不行，或者说「全面 review 一下」。两边各自把项目读一遍，各出一份问题清单，按阻塞、应修、可改三档排好，Claude 合并去重之后再让 Codex 审一轮合并稿。这里有两把尺子，一把是产品层，看能不能上架、能不能收费、能不能交付给客户；另一把是代码层，按模块一块一块找 bug 和隐患，每个模块单独派一条 Codex 的只读线去查。最后给我不足清单和先做的三件事，我选做哪几件，选中的直接转到第三种。

第三种是协同，对应方案已经有了，要修改或者推进项目。方案可以是 Plan 模式出来的，可以是前两种的结论，也可以是我口述清楚到能写出验收标准的。这一种不再讨论，Claude 直接拆活、分模型、派活、验收，最后交完工报告。

另外两个小规则。项目里有上一场没干完的，它接着那场往下做，不重新开；一个小时之内能干完的小活，它不走这套流程，直接做掉。

## 模型谁来定

模型这一块最后拍板的一直是我，因为两边额度还剩多少、这个月想怎么花，只有我自己最清楚。

开场那一行，它会把这次的配置全部报出来，总调度用哪个模型、审方案用哪个、执行往哪边倾斜，还有两边的额度现在是宽、正常、紧还是空。额度是它自己跑一个探针读出来的，一秒多读完两边，不花额度。我想改哪一项直接说一句，改了以后这一整场都按我说的来，记在账本里。我要是提前说过「这次每件活都要我来指定型号」，它就会逐件问，而且额度一旦读到紧或者空，它一定会停下来专门问我，是刷重置卡、降一档还是等重置。

然后到派活之前，Claude 会把项目分区分块，拆成一件件两个小时之内能做完、能单独验收的小活，每件活判四样东西，难不难、怎么算做完、需要什么环境、两边额度往哪边倾斜，再定交给哪个型号、用什么强度、时间上限多少、谁来审。执行方有两条梯子，GPT 这边是 6.1 Sol 到 Astra，Claude 这边是 Haiku、Sonnet 到 Opus，先看两边额度定走哪条，Codex 宽或者手里有重置卡就默认走 Codex，几个项目一起开发的时候也走 Codex，把 Claude 的额度留给总调度；Codex 紧了再走 Claude 这边的梯子。定了梯子再按活选层，比如照着设计稿做页面、补测试这种规格清楚的活，给便宜的 6.1 Sol 或者 Sonnet，Sol 的消耗大概只有 Astra 的五分之一；机械批量和只读取证给 Haiku 或者 Sol 的低强度；跨模块的底座、根因查不出来的 bug，才给最强的 Astra 或者 Opus；钱、权限、数据迁移这一类，谁写的 Claude 都必须亲自去核实际状态。这张拆分表每件活一行，写着给谁、为什么、谁审、大概多久，派之前先报给我，我改哪条它就停哪条重派。

我说过的话优先级最高。比如我说一句「最近一段时间多用 GPT 那边」，它就会把更多的活往 Codex 派，这句话记在账本里，这段时间都管用；我说「这个月难活一律用 Astra」，它就照着排，就算跟额度冲突了也照我的话派，再告诉我一声代价是什么。

## 派出去以后

活派出去，各条线各干各的，干完统一交回来。验收的人和干活的人一定是不同型号，Astra 写的让 6.1 Sol 复核，Sol 写的让 Astra 复核，或者 Claude 自己把验收命令重新跑一遍；有界面的活，Claude 要自己在模拟器里按真实用户的任务走一遍、逐张看截图，阻塞和应修清零才算过。没通过的，把已有的改动和失败输出附在任务书后面重新派，不让下一个执行者从头读仓库。全部过了以后，Claude 在合并后的主干上再亲自跑一遍完整的测试，然后交我一份完工报告，里面有做了什么、怎么验的、没做完的，和两边额度从多少用到多少。

## 踩过的坑，现在都成了规矩

这个技能里面最值钱的部分，我个人感觉是下面这些，每一条都是实际干活的时候摔出来的，摔一次当天就写进去。

- 止损。有一条做性能的线跑了七个半小时，烧掉我三成周额度，还在模拟器上抠十几毫秒的数字，而模拟器测图形性能本来就不是特别的准。现在每条线派出去就带时间上限，常规两小时、难活四小时、窄回归一小时，到点脚本直接把它停掉，停掉的线不自动重派；每小时 Claude 看一次指标走势，不往目标收敛马上停。停下来之后 Claude 先判是完成线定错了还是方法错了，然后三选一，把已经验证的改进收下发版、交真机去判、或者重写一份更窄的任务书再派。同一个问题 Codex 两轮没收敛，第三轮换 Claude 这边的主模型，Fable 或者 Opus，亲自查根因、写清方案，Codex 只照方案实现，不再让它自己摸索。
- 两边额度都紧的时候有一条梯子，降一档强度，并行改串行，不急的挂到重置后，问我刷不刷重置卡，最后才是停。每一步记进调度记录。
- 一份任务书只放一个目标。以前一份塞七八件事，Codex 跑四到八个小时，交回来一半写着待处理。现在独立的事超过三件就拆成多份并行，每份两小时内能做完、能验收。
- 完成线必须能失败。终端卡顿那件没写清楚多顺才算完，Codex 修了能修的就交差。现在「顺滑、好看、稳定」这类词不许直接进任务书，要翻成数字或者附样张，比如持续输出时主线程低于 15%，达不到就写达不到、差多少，不许交成完成。
- 要点界面的验收不留在沙箱里。Codex 在沙箱里起不了模拟器，验收只能写一句待验证，结果第一版装到手机上整屏点不动。现在这类验收要么 Claude 自己跑，要么让 Codex 开全权限跑，但任务书里把边界写死，只改本工作目录、临时端口、自建模拟器、不碰生产和用户数据、不提交。
- 验收夹具照我的真实用法造。终端滑动和中文排版两个问题都是我在真机上发现的，测试只回放过纯英文的 shell 输出，没人看过全屏模式加中文加状态栏 emoji 在手机上的样子。现在要先读我的实际配置，把真实程序的输出录成字节流回放进测试。
- 同时跑的模拟器最多两台。三台一起跑，主机负载两百多，把同一台机器上的微信接入拖挂了。现在每条线自建自删自己的设备，重活跑完先查同机的生产服务还活着。
- 合并后立刻把该线的工作目录挪进废纸篓。每条线一个 worktree 各带十几 G 缓存，两天攒出 256 G；还有一次收尾脚本把 846 个截图录屏一起提交进了分支。现在任务书里的路径一律写绝对路径，收尾脚本排除所有产物目录，Claude 合并前必看一眼改了多少文件。
- 发版前 Claude 必须在合并后的主干上亲自复跑一组完整测试。Codex 自测全过，合并后照样抓到失败，它报的数字只当参考。
- 视觉设计 Claude 先出样张。设计直接交给 Codex，我连着说了三次丑，现在是 Claude 出样张、我点头、Codex 照着做。
- 实现默认交 Codex，但是不再一刀切。10 月初我回头把七场实跑的记录对了一遍，开工的五场里 Codex 只在两场真正写过代码，剩下都是 Claude 自己闷头干完的，规矩写进去了模型也不一定照做，所以 10 月 5 号我把 Claude 的子代理全删了，实现一律交 Codex。用了几天发现一刀切也不对，Codex 紧的时候 Claude 这边的 Haiku 和 Sonnet 其实闲着，所以 10 月 10 号改成上面说的两条梯子，哪边宽走哪边；Codex 宽的时候要是把活派给了 Claude，拆分表里必须写一句为什么，防止又回到老路。

## 哪些已经验证过，哪些还没

探讨、派活、验收、止损这些已经跑了两个多星期，9 月底对账过七场，10 月 7、8 号给 App 做手机版又跑了二十多条线，上面说的规矩就是从这些场次里来的。1.4 版新加的「说一句用 skill 它自己判断走哪种用法」和「开场报一行不等答复」，还没有在一场完整的真实项目里走过，这是接下来第一场要验的东西。复盘按模块并行派只读线的做法，和 Claude 这边的梯子，都是这两天刚写的，同样等下一场。

它也有一些不是特别的方便的地方。它现在是按两边订阅都有来设计的，审方案、派活的两份脚本都要本机装着 Codex 命令行，版本要 0.160 以上才能调新型号；只订阅了 Claude 的朋友，拆活、按层选型号省额度这套思路能用上，但 skill 还没做「没有 Codex」的分支，审方案会变成 Claude 审自己，两个模型互相挑错那部分就没有了，这个要另外加才行。另外跑一场探讨要用掉两边的额度和差不多半小时到一小时的时间。但是因为我自己两边订阅本来就都有，大活返工一次的代价又远比这个高，所以这一点对我个人来讲影响不大。

总之我个人来讲，手里 Claude 和 GPT 两边订阅都有、经常让 AI 干一些一个小时干不完的大活的朋友，这个东西非常值得试一下；平时只改改小东西的朋友，其实不用特别的着急。想装的朋友，在仓库里跑一下 `./install.sh`，重开一个 Claude Code 会话，说一句「用 skill」就可以了。

OK 那，这些就是我这段时间做 Roadstar 的一些体会，希望对大家有一定的参考价值。
