# Roadstar 社区数据回传（2026-10-14 起）

用户同意一次以后，Roadstar 每跑完一场派活，就自动把这一场「什么活给了哪个型号、做没做完」的统计传到一个公开的 GitHub 仓库。作者每周把大家的数据汇总一次，更新「社区经验表」，跟着新版本发出去，让每个人一装上就能用上所有人攒下的派活经验。

## 1 用户会看到什么

第一次开场时，Roadstar 在开场那一行后面只问一次：

> 要不要自动回传这台机器的派活统计，帮大家把「什么活给什么型号」调准？
> 传的只有：活的类别、型号、强度、做没做完、用时、额度差、skill 版本、哪一周。不传代码、路径、项目名和任何你写的文字。
> 传到公开仓库 github.com/Rurutia-Artemis/roadstar-data，用你本机的 gh 以你的 GitHub 账号开一条 Issue，所有人都看得到。
> 随时可以关：说一句「关掉回传」，或者设环境变量 `ROADSTAR_TELEMETRY=0`。
> 要开吗？（默认不开）

回答记在本机 `~/.config/roadstar/telemetry.json`，以后不再问。中文、英文、日文三种说法，按用户的会话语言选。

## 2 传什么，不传什么

一次回传是一批，顶层只有 `schema`（固定 1）、`client`（固定 roadstar）、`skill_version` 和 `records`。每一条记录只有下面 12 个字段，全部是固定选项或取整后的数字，没有一个自由填写的文本字段（完整格式：`skill/references/dispatch-v1.schema.json`，和数据仓库的 `schema/dispatch-v1.json` 是同一份）：

| 字段 | 内容 | 例 |
|---|---|---|
| `id` | 本地记录的 sha1 前 16 位，只用来去重 | `3f2a9c0d1e4b5a67` |
| `week` | 年和周，不记具体时间 | `2026-W42` |
| `class` | 活的类别，11 个固定词之一 | `页面实现` |
| `model` | 型号，归一后的固定名 | `haiku`、`gpt-6.1-sol` |
| `model_version` | 型号版本 | `5.5` |
| `effort` | 强度 | `high` |
| `outcome` | `done` / `partial` / `stalled` / `failed` | `done` |
| `done_ratio` | 过了几成检查项，取到 0.1 | `0.9` |
| `minutes` | 用时，取到 5 分钟 | `35` |
| `escalated` | 有没有升级补全 | `true` |
| `quota_delta` | 额度差，取整 | `claude_week=2` |
| `plan` | 订阅档位，固定选项 | `max` / `pro` / `unknown` |

不传：代码、文件名、路径、项目名、任务书、报告、报错文字、Git 信息、机器名、具体时间。

这些字段在发送前由本机脚本检查一遍，到了仓库再由 GitHub Action 检查一遍，多出任何一个字段、或者某个值不在固定选项里，整条拒收。

## 3 什么时候传

- 每场完工报告时传一次，把这一场所有线的记录打成一批发出去，完工报告里写一行「已回传 12 条，内容见 `~/.config/roadstar/uploads/2026-10-14-xxxx.json`」。
- 干活中途从不发送，不占派活的时间和额度。
- 传失败（没装 gh、没登录、断网）就留在本机，下一场完工时一起补传；补不上不报错、不打扰。
- 每一批发送前都先在本机存一份原样副本，用户随时能打开看到底发了什么。

## 4 传到哪里，怎么传

- 目的地：公开仓库 `Rurutia-Artemis/roadstar-data`，只收数据、不放代码以外的东西。
- 方式：用户本机的 `gh issue create`，标题 `dispatch-data · schema 1 · 2026-W42`，正文第一行是 `<!-- roadstar-dispatch-data -->`，下面是一段 JSON。提交人加不了标签，标签由仓库里的校验 Action 加。任何 GitHub 用户都能在公开仓库开 Issue，不需要仓库的写权限。
- 会公开什么：这条 Issue 带用户的 GitHub 用户名。同意时已经说清楚；想撤回，删掉自己那条 Issue 即可，汇总脚本下次运行会把它排除。
- 以后可选：如果很多人在意匿名，再加一个中转（Cloudflare Worker 校验后用机器人账号代发），用户就不用露出用户名。第一版不做。

## 5 安全与透明怎么保证

1. 结构上传不出隐私：只有白名单字段和固定选项，没有自由文本。
2. 默认关闭，问一次，同意了才开。
3. 本机留底：每一批原样存在本机，完工报告写明路径。
4. 一句话或一个环境变量就能关，撤回就是删自己的 Issue。
5. 全公开可审计：数据、校验 Action、汇总脚本都在公开仓库里。
6. 发送代码是一个只用标准库的小文件，目的地写死；测试断言发出去的内容只含白名单字段，多一个字段测试就失败。

## 6 汇总怎么做

- 每条 Issue 进来，仓库里的 Action 先校验：格式对的打 `accepted` 标签，不对的自动关闭并说明原因。
- 防刷：同一个提交人每周最多计 50 条；社区表按「有多少不同的人提交过」加权，一个人刷再多条也只算一个人的意见。
- 每周汇总一次（见第 7 节），产出两份文件提交到数据仓库：机器读的 `community-table.json`，和人看的 `community-table.md`。
- 型号换代：每条带型号版本，新版本出来后，旧版本的数据单独成组，不和新版本混算。

## 7 迭代节奏

- 每周日自动汇总一次。周一，作者用 Roadstar 跑「社区经验周报」：哪些类别的数据够了（至少 3 个不同的人、合计 10 条以上）、起步层该降还是该升、和上周比有什么变化。作者拍板以后，把新的社区表打进下一个版本发布。
- 判断「差不多准了」：常见的类别（取证、批量、页面实现、窄回归、复核）在起步层的完成率都到 85% 以上、升级补全率在 15% 以下，并且连续三周没有起步层调整，就改成每月汇总一次。之后有新型号上线，再回到每周。
- 所有人用同一张表（主席 2026-10-14 定）：社区表写进 SKILL.md 第 8 节、发新版本，用户开场时会被提醒更新。本机记录只用来回传和校准本机的用时预估，不单独改本机的起步层，这样大家朝一个方向变好，回传数据也能放在一起比。
- 谁来改表（主席 2026-10-16 定）：打分和迭代由 Claude 自己持有，不传 Google 文档、不让主席逐条拍板。主席每周说一句「可以迭代了」，Claude 按门槛改表、发版，周报只写结论；没说那句就只出周报不改表。1.12 先手工按这条做，自动迭代脚本以后再加。

## 8 现在的状态

- 已上线（2026-10-14）：数据仓库 https://github.com/Rurutia-Artemis/roadstar-data（校验与每周汇总两个 Action）、Roadstar 1.11.0 的 `skill/scripts/telemetry.py` 与开场同意流程、README 三语说明。
- 实测：用临时项目真发一条，Issue 被自动打上 `accepted`；手动提交一条夹带路径字段的，被打上 `rejected`、评论只写原因、自动关闭；手动触发汇总，社区表出现这一条且不含用户名。测试 Issue 已删除，社区表已清空。
- 每周周报：云端定时任务每周一 10:00 JST 读社区表和 Roadstar 第 8 节的表，写一份周报文档给作者。
