## 3 用户视角的完整流程，一步一屏

### 3.0 哪些屏要答、哪些只看一眼

Roadstar 现在的原则是开场报一行不等答复，只在必要时问。产品化之后面板变多，取舍定成四条：

1. 一场只出一张面板，放在开场；之后每一屏只写「变了的」，不重复面板。
2. 每一屏都有默认答案，主席沉默就按默认跑；面板最后一行固定是「要改说一声，不改我就跑」。
3. 必须等答复的点和现在一样只有三处：功能地图分档、纪要里开不开工、取舍类争议。新加一处：策略是「质量优先」而额度不够时，停下来问（主席选质量就是说宁可等）。
4. 面板长度上限 14 行，排活表每件一行，超过 8 件折成「前 8 件 + 其余 N 件同类」；续接和协同用三行压缩版。

| 屏 | 什么时候出 | 要不要答 | 沉默等于 |
|---|---|---|---|
| 接入与额度面板 | 开场 | 看一眼 | 按读数跑 |
| 策略 | 面板最后一行 | 看一眼 | 自动分配（或 quota.json 里设的默认） |
| 本项目分配预览 | 面板之后 | 看一眼 | 按预览跑 |
| 探讨开场说明 | 探讨用法，预览之后 | 看一眼 | 按默认轮数和型号跑 |
| 功能地图分档 | 探讨，内环前 | 要答，只改不同意的 | 按预填分档 |
| 纪要 + 排活表 | 停机后 | 要答，开不开工 | 不开工（这是现在的规矩，不变） |
| 执行中进度 | 主席问、系统催促、或预计完工时刻变动超过 30 分钟 | 看一眼 | 继续 |
| 完工报告 | 全部验收后 | 看一眼 | 结束 |

## 4 额度估算方法

### 4.1 每家怎么读

| 家 | 读法 | 能读到什么 | 读不到时 | 置信度 |
|---|---|---|---|---|
| Claude | 现有探针（Claude Code 控制协议 `get_usage`） | 5 小时窗、周窗、Fable 单列各自的已用百分比和重置时刻、套餐 | 面板写「读不到（原因）」，档位按「紧」保守处理，常驻活退回 Codex | 高 |
| Codex | 现有探针（app-server `account/rateLimits/read`） | 周窗、5 小时窗、重置卡张数、credits 余额、套餐；实时失败退回本地 rollout 记录并标多久前 | rollout 记录标「N 小时前」，置信度降到中；都读不到按「紧」 | 高（实时）/ 中（rollout） |
| Grok | `grok models` 判登录和可用型号；额度没有接口 | 登录状态、型号表 | 一律「？」。用户在 `quota.json` 自报档位后，用 `grok sessions` + `grok usage <id>` 把本机会话的 token 累加成「本机累计」和自报对照（汇总可行性待实测） | 低（自报） |
| API key | 只看环境变量名有没有（`ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`XAI_API_KEY`、`DEEPSEEK_API_KEY`、`MOONSHOT_API_KEY`、`DASHSCOPE_API_KEY`、`ZHIPUAI_API_KEY`、`MINIMAX_API_KEY`，名单放 `providers.json`，不读值、不存值） | 有没有、哪家 | 没有就一行「无」 | 有无：高；余额：各家余额接口待查，1.12 不读 |
| 用户自报 | `quota.json`：Grok 档位、各家 API 月预算（美元）、默认策略 | 预算上限 | 没填就「未填」 | 低，永远标「自报」 |

v0 原则一落到这里的做法：自报的数字只决定「上限」，从不当「余额」。面板里自报项带「自报」两个字；本机累计（Grok 会话费用、1.13 起 API 执行器的记录）超过自报预算时，面板把那家标成「矛盾，按已超预算处理」，不派。读数和自报冲突，读数赢。

### 4.2 统一单位：标准件

主席看到的是「还能派多少活」，所以单位定成「件」，而不用「Sonnet 等价小时」。理由有两条。件数直接对应拆分表的行数，主席能把「还能派 46 件」和「这场 6 件」放一起看；小时要先知道哪个型号跑多久，多一层换算。等价小时在内部仍然用，它是件数系数的中间量。

定义：1 标准件 = 一条「页面实现」类、6.1 Sol / high 或 Sonnet、约 35 分钟的执行线平均扣掉的额度。

每家的「还能派」= 可用百分点 ÷ 该家每标准件扣的百分点。可用百分点 = 90 − 已用（留一成底，现有规矩）。每标准件扣几个点，从 `.meta` 的 `quota_delta` 学：取同一家近 30 条记录，把每条按型号和强度倍率折成标准件数，点数 ÷ 件数取中位数。样本不到 10 条时系数「未校准」，面板件数写「约」、置信度「低」，并且另给百分点。

折算到标准件的倍率（初值，来源是 `models.md` 里的 API 价比和相对消耗，订阅扣额倍数没有官方数字，靠 `quota_delta` 校准）：

| 侧 | 型号 | 倍率 | 来源 |
|---|---|---|---|
| Claude | Haiku 5.5 | 0.05 | API 价约 Sonnet 的二十分之一 |
| Claude | Sonnet 5.5 | 1 | 基准 |
| Claude | Opus 5.5 | 2 | API 输入价 $4 对 $2 |
| Claude | Fable 5.1 | 5 | API 输入价 $10 对 $2；另吃 Fable 单列 |
| Codex | 6.1 Sol | 1 | 基准 |
| Codex | Astra | 5 | models.md「约 Astra 的五分之一」 |
| Codex | Luna | 0.05 | models.md「约 6.1 Sol 的二十分之一」 |
| Grok | grok-4.7 / build-fast | 待查 | 没有价格和额度数据，不折算 |

强度倍率：low 0.7、medium 1、high 1.3、xhigh 2（xhigh 实测把活拉长一倍以上，先按用时翻倍估额度，待校准）。

### 4.3 重置卡和重置时刻怎么折

- Codex 重置卡：一张 = 把周窗清零一次 = 再加 90 个可用点。面板单独一行「可解锁」，不计入「现有」，因为现有规矩是「到顶时停下等主席刷卡」，刷不刷由主席定。
- 周窗重置时刻：如果本场预计完工时刻晚于某家的重置时刻，重置后那段按满额算，面板写「X 时回满」。排期时，排在重置后的线按重置后的额度判档，不被现在的「空」挡住（第 6 节）。
- Claude 5 小时窗和 Codex 5 小时窗：限制的是并发，不是总量。不折件数，只用来定并行线上限：并行线数 × 每线平均扣 5 小时窗的点数 ≤ 85 − 当前已用。系数同样从 `quota_delta` 的 `*_5h` 记录学，没数据时并行上限取现有规矩的 3 条 Codex 加 1 条 Claude。
- Fable 单列：只影响主会话和 Fable 子代理，单独一行显示，不进件数。
- credits：动真钱，只显示「有余额」，不折件数，不进分配；主席授权才用（现有规矩）。
- 合计：各家「现有」里置信度中以上的相加；「可解锁」另列。置信度取各家里最低的那个。

### 4.4 「够不够这场」

探讨阶段：功能地图 2 次 Astra 调用 + 审稿 N 轮 × 每轮 1 次 Astra / high，每次按「审方案」类的默认用时和 Astra 倍率折件；主会话按 5 小时窗观察，不折件。执行阶段：拆分表每件按类别、型号、强度折件再相加。两个数都和「现有」比：够就不说话；不够就在面板或排活表后写「第 4 件起 Codex 会到 85%，到时按第 5 节降级，或你刷一张重置卡」。

## 5 策略：四种加一个开关

### 5.1 策略在哪一层起作用

派活判断的顺序是：主席硬话 > 执行环境 > 验收条件 > 难度（定类别）> 策略（定起步层）> 额度方向（定走哪条梯子）。策略只改起步层，碰壁升级链、经验回路、审查人跨家、钱和权限由 Argo 亲验，这些在四种策略下一个字不变。所以策略和现有「起步层表 + 碰壁升级 + 经验回路」的关系是：自动分配就是 SKILL §8 那张表本身；质量优先是每类往梯子上挪、挪到顶为止；省着用是往下挪、挪到最低能做的那层为止；赶时间不挪层，改的是并行、上限和复核方式。

`.meta` 加一个 `strategy` 字段（auto / quality / thrift / rush），本机经验表按策略分组看；回传字段等 schema 2 和 v0 的 `score` 一起加，1.12 不动 schema。起步层表仍然只由社区数据按 10-14 的规矩更新，策略偏移是运行时叠在表上的，不写回表。

### 5.3 额度不够时怎么降、怎么提醒

按顺序走，每走一步在进度屏报一行，记进调度记录：

1. 同家降一档强度（xhigh → high → medium）。
2. 同类活换到另一条梯子（Codex ↔ Claude），这算换方向，自动分配和省着用下直接换并报一行，质量优先下停下来问。
3. 并行改串行，排在 5 小时窗滚动之后。
4. 不急的挂到周窗重置之后，报重置时刻。
5. 问主席刷不刷重置卡，说法沿用 division-of-labor 第 11 节那句。
6. 停。

四种策略的差别只在第 2 步和第 5 步：质量优先第 2 步就停下来问，不自动降型号；省着用第 5 步不问刷卡，直接挂起；赶时间第 3 步不串行，先问刷卡。

提醒的写法固定：「<哪家> 到 <几成>，第 <几> 件从 <A> 降到 <B>，预计完工 <原> → <新>；想保质量就 <刷卡 / 等 X 时重置>，说一声我换回来。」

## 6 预估用时和完成时刻

### 6.1 每件活的预估

预估用时 = 执行线时间 + 复核线时间 + Argo 时间。

- 执行线时间 = 该格的 P50 × 缓冲。P50 的来源按顺序取第一个有的：本机「类别 × 型号 × 强度」样本 ≥ 5 条；本机「型号 × 强度」样本 ≥ 5 条；社区表同格；默认值表。缓冲先用 1.3，某格样本到 10 条后改用该格实测 P80，不再乘缓冲。
- 复核线时间 = 「复核」类 P50，默认 20 分钟。
- Argo 时间 = 写任务书 10 分钟 + 验收 15 分钟 + 合并 5 分钟。这三个是初值，没有实测过；从账本调度记录的时间戳（派出时刻减上一件验收完的时刻）学，样本够了换实测中位数。

|---|---|---|

### 6.2 完成时刻怎么排

`schedule.py` 读拆分表（plan §10）、依赖列、并行线上限、各家额度窗口，做一次最简单的排程：

1. 执行线按依赖拓扑排序，并行线数不超过上限（策略定，模拟器线 ≤ 2）。
2. Argo 是单线程：任务书、验收、合并串行排在一条「Argo 线」上。关键路径经常在这条线上，排活表要把它算进去，否则 6 条线并行时完工时刻会乐观一个多小时。
3. 额度窗口：每条线累加预计扣点，某家 5 小时窗到 85% 就把后面的线推到窗口滚动之后；周窗到 85% 就按第 5.3 节降级后重算；周窗重置时刻之后的线按满额算。
4. 主席要答的点（样张点头、争议裁决）不计入，表里写「从你说开工起算，等你点头的时间不算」。
5. 输出：每件的预计完成时刻（验收完的时刻，JST）、线上工时合计、关键路径（哪几件串成最长那条）、并行线数、预计全部完工时刻、置信度（取各件里最低的）。

时刻用 JST 显示，和探针一致。

### 6.3 差太多怎么修

- 跑的时候：每小时检查点（现有规矩）用已完成的件重算剩余，预计完工时刻变动超过 30 分钟才报一行，否则不开口。
- 完工时：报告写「预估对账」一段（第 3.8 节），每件预估、实际、偏差，`.meta` 加 `est_minutes`，`dispatch-stats.py` 加「预估偏差」列。
- 校准：`dispatch-stats.py --calibrate` 把本机各格的 P50 / P80 写进 `~/.config/roadstar/estimates.json`，下一场优先读它。这只改本机的用时预估，不改起步层，和 10-14「本机记录不单独改本机起步层」的规矩不冲突。
- 结构性偏差：某格连续 3 场偏差同向超过 50%，完工报告提一句「这类活的默认值建议改成 X」；偏差来自碰壁升级的不改默认值，走升级链统计。
