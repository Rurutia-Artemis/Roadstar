## 2026-10-16 · 直接调 codex exec 没有时间上限，一轮网页打磨跑了 73 分钟

- 现象：Frontier 网站第二轮打磨（12 条 CSS 与排版改动）用 `codex exec -m gpt-6-astra -c model_reasoning_effort=high` 直接派出去，没有 `--max-minutes`，没有进度文件，没有 stall-watch，跑到 73 分钟被 Argo 手动杀掉；Codex 周额度从 7% 到 8%。
- 根因：这次是在 Frontier 会话里用 call-codex 的裸命令派的活，绕过了 Roadstar 的 `dex-exec.sh`，而止损、进度文件、停线这些纪律全在 dex-exec.sh 里，裸命令一样都没有。Codex 自己又因为沙箱起不了浏览器，用 Node 模拟 DOM 反复自验，把一个半小时的活做成了开放式优化（escalation-and-learning 第 3 节描述过的「空转」）。
- 要改的规矩：
  1. 任何会话派 Codex，一律走 `dex-exec.sh`，哪怕只有一件活、不在 Roadstar 场次里；call-codex skill 的命令示例改成带 `--max-minutes` 的 dex-exec 调用，裸 `codex exec` 只留给一句话提问。
  2. 打磨、修样式这类活默认上限 30 分钟，一张清单最多 6 条，多了拆两线。
  3. 任务书里写明「验证方式只用 X」（比如只跑 build 和 unittest），禁止执行方自己发明验证手段；视觉验收由 Argo 截图，Codex 不模拟。
  4. stall-watch 对没有进度文件的线要能报「无进度文件」并在 20 分钟时停线。
  5. 1.12 的打分要把「超时被杀」记成 `outcome=timed_out`，和 stalled 分开统计。

## 2026-10-16 · 上限不能拍脑袋，要先估时再定

- 现象：Frontier 网站重做（单文件静态站，几百行模板加一个生成脚本）给了两小时上限，主席指出这种活 Claude 自己做 10 到 15 分钟就完，两小时的上限等于没有上限。
- 要改的规矩：
  1. 任务书必须先写「预计用时」，由 Argo 按活的类型和改动范围估，上限 = 预计的两倍，最多不超过类型默认值（见下表），不许直接套常规 120 分钟。
  2. 类型默认值（起步，按回传数据调）：单文件网页或模板重做 20 分钟；样式与排版打磨清单（≤6 条）15 分钟；脚本或配置（≤200 行）20 分钟；规格清楚的页面实现 40 分钟；跨模块实现 90 分钟；根因诊断 60 分钟；取证与批量 15 分钟。
  3. 到预计用时的一半还没有一个检查项 pass，Argo 看一眼进度文件；到预计用时还没完成就停线收口，不等上限。
  4. 把「预计用时 / 实际用时」两个数记进 `.meta` 并回传，1.12 的自动迭代按实际用时校准默认值。

## 2026-10-19 · `perl -e 'alarm N; exec @ARGV'` 包 `codex exec` 不能真正止损

现象：前沿谈全站上锁一活用 `perl alarm 2400` 包着 `codex exec` 派出，40 分钟到点后 node 壳子死了，但原生子进程 `codex-darwin-arm64/.../codex exec` 变成孤儿（PPID 1）继续跑，期间一个文件没改、stdout 为空；同时机器上 Mia 的八条 Codex 线和 Swift 编译把 CPU 占满。
原因：SIGALRM 只打到 exec 出来的那个进程（node 壳），原生子进程不在同一信号路径上。
规矩：派 Codex 一律走 `dex-exec.sh --max-minutes`（到点 TERM 整棵树、十秒后 KILL），裸 `codex exec` 加 `perl alarm` 只用于一句话提问；机器上已有超过四条 Codex 线在跑时，新活先排队或把上限按两倍放宽，并在派活前跑一次 `ps` 看负载。
