# 纪要模板（写给不看代码的主席）

停机后主席只看这一份。他不认识账本代号，不读命令，只想知道三件事：结果是什么、谁做什么、他要答什么。按下面顺序写，每段只写该段的内容，不写过程。

```markdown
**结果**：方案定了，可以开工。／还差一件事：…。／卡住了，要你选（见下）。

**我们商量出来的方案**
三到五句大白话。先说现在的问题是什么，再说打算做成什么样，最后说怎么算做完。不写文件名、不写字段、不写命令。

**讨论中改了什么**
- 原来打算…，Codex 指出…（一句说清后果），改成…。
- 原来打算…，Codex 用实际记录证明…，改成…。
- 原来…，改成…。
另外还修了 N 处细节（一句概括是哪类）。

**你要做的**
1. 分工按下面的推荐来，还是改哪几条？（例：第 3 件换 Opus）
2. 一句话问题。选项：A / B。我的建议：A，因为…。（只问做不做、花多少、要什么舍什么。）
除了第 1 条没有别的要问，就只留第 1 条。

**推荐谁做什么**
（你开场选的是：执行按我每件推荐，这周 Codex 多，能派的实现推荐给 Codex）
| 事 | 推荐给谁 | 为什么 | 备选 | 大概多久 |
|---|---|---|---|---|
| 人话任务名 | 我 / Opus / Sonnet / Codex 的 Astra / Codex 的 6.1 Sol / 网页 Pro / 你，后接强度 | 一句话：难在哪或省在哪 | 换人时的下一个人选 | 半小时 / 一两个小时 / 半天到一天 |

按推荐来，还是改哪几条？

细节在：docs/roadstar/<日期>-<slug>/
```

写法要求：

- 「推荐给谁」和「备选」只用这几种写法：「我」「Opus」「Sonnet」「Codex 的 Astra」「Codex 的 6.1 Sol」「网页 Pro」「你」，后面用「· 低 / 中 / 高 / 很高」写强度。Argo / Dex 这些标签只在账本和文件里出现。
- 「为什么」每件一句，说这件活难在哪、为什么配这个人，或者省在哪；表前一句写主席开场选的方向。
- 议题编号、阻塞 / 建议这类严重度标签、字段名、命令、工具名、脚本名，一个都不进纪要。专有名词要用就在括号里解释一次。
- 「讨论中改了什么」只挑改变结果的，最多三条；每条都要说清「不改会怎样」。
- 「你要做的」第 1 条固定问分工；其余每件先选项后建议，能一个字答。
- 「大概多久」用分量换算：小 = 半小时内，中 = 一两个小时，大 = 半天到一天；是估计，纪要里说是估计。
- 整份一屏内。写完自检：一个没看过代码的人能不能只靠它知道结果、谁做什么、要答什么；不能就重写。
- 逐轮模式的每轮汇报同一配方，「讨论中改了什么」只写本轮。

## 例子（本仓库 audit-usage 那场）

**结果**：方案定了，可以开工。

**我们商量出来的方案**
现在盘点哪些 skill 该退役时，脚本只数「在 Claude 里被明确启动了几次」，数不到 Codex 那边的使用，也数不到通过工具接口和参考文件的使用，所以会把还在用的 skill 当成没人用。这次改成数四种使用：Claude 里启动、工具接口调用、Codex 里读过、参考文件被读过；再加一列「数得全不全」，数不全的 skill 一律不进退役名单。做完的标准：老功能一个字不变；整机扫一遍 60 秒内（试跑 30 秒）；一套自动测试证明四种数法都数对，不多算也不漏算。

**讨论中改了什么**
- 原来打算按文字找「启动了某 skill」这句话，Codex 指出说明文档里也有这句，会多算，改成只认真正的启动记录。
- 原来用一条简单规则判断 Codex 有没有读过某个 skill，Codex 用实际记录证明它既会多算（把搜索关键词当成文件）也会漏算（带管道的命令），改成按命令逐段解析，看不懂的命令标「没数到」而不是算零。
- 原来扫描超时就只看近 90 天，Codex 指出这是偷偷缩目标，删掉了，改成先实测，30 秒够用。
另外还修了九处细节（缓存怎么失效、测试怎么写、措辞前后矛盾）。

**你要做的**
1. 分工按下面的推荐来，还是改哪几条？（例：第 3 件换 Opus）

**推荐谁做什么**
（你开场选的是：执行按我每件推荐；这周 Codex 多，三件实现都推荐给 Codex）
| 事 | 推荐给谁 | 为什么 | 备选 | 大概多久 |
|---|---|---|---|---|
| 从两边日志抽真实样本、写测试用例 | Codex 的 6.1 Sol · 中 | 照着日志挑样本、按格式写用例，不用做取舍；6.1 Sol 消耗约 Astra 的五分之一 | Sonnet · 中 | 一两个小时 |
| 写统计脚本和缓存 | Codex 的 Astra · 高 | 四种数法要同时做到不多算不漏算，还要管缓存失效，最容易出错，给最强的 | Opus · 很高 | 半天到一天 |
| 接进现有盘点脚本、跑回归 | Codex 的 6.1 Sol · 中 | 照现有接口接线，老功能对照改前输出就能验，在沙箱里跑得通 | Sonnet · 中 | 半小时 |

按推荐来，还是改哪几条？

## 完工报告（开工后的第三次开口）

```markdown
**做完了**，可以用了。／**做了一半**，卡在…。

做了什么：一两句人话，对应纪要里的方案。

怎么验的：老功能对照改前输出，一字不差；整机跑一遍 X 秒；N 条自动测试全部通过；Codex 复核了我写的部分，我复核了它写的部分，各挑出几处已修。（数字写实际值，没做的项写「没做」。）

没做完的：无。／逐条列，每条一句说卡在哪。

你要做的：没有。／一句话 + 选项。

额度：Claude 本周从 X% 到 Y%，Codex 从 X% 到 Y%。

记录在：docs/roadstar/<日期>-<slug>/，共享记忆已写。
```

要求同纪要：自称「我」，对方写「Codex」，不出现文件名以外的技术名词；验证结果只写跑过的，测试挂了就写挂了几个；额度写两边读数差。
