# 碰壁止损、升级补全与派活经验回路

主席 2026-10-14 定：Roadstar 要靠真干活的结果自己学会「什么活派给什么型号最合适」，并且一分额度都不白烧。一条线做到九成、剩下一成碰壁几次，就马上停，把做完的九成收下，只把剩下那一成交给高一级的型号补全。两家都有时这样做，只用 Claude（单家模式）时也一样，Haiku、Sonnet、Opus、Fable 四层同样按这套升级和学习。

## 1 型号的升级链

一件活从经验表推荐的最低一层起步，碰壁才往上走，每次只升一级：

- Claude：Haiku 5.5 → Sonnet 5.5 → Opus 5.5 → Fable 5.1（Fable 只接补全或根因，不从头接整件活）
- Codex：6.1 Sol → Astra → 交 Claude 的 Opus 或 Fable（跨家补全，按额度方向）
- 强度也算一级：同一型号 medium → high → xhigh。先升强度还是先升型号，看碰壁原因：缺知识、缺判断就升型号；只是想得不够深就升强度。

升到 Fable 还碰壁，或者同一件活已经升过两次，就交 Argo 亲自诊断或问主席（division-of-labor 第 10 节）。

## 2 进度文件：每条线都要写

任务书「目标与做完的样子」把完成线拆成编号检查项 `C1 … Cn`，每项一条能失败的验收命令或可观测条件。执行方（Codex 线和 Claude 子代理一样）每试一次某个检查项，就往 `<plan-dir>/rounds/exec-T<n>.progress` 追加一行，用制表符分隔：

```
<ISO 时间>	<检查项编号>	<pass|fail>	<一句证据：命令、报错首行或数字>
```

没有这个文件的线，Argo 看不出它卡在哪，所以任务书「资源上限与止损」一节必须写明这个要求。

## 3 什么时候停

`scripts/stall-watch.py <progress 文件> --cap <分钟> --started <开始时间>` 读进度文件，输出一行状态。Argo 派活后用 Monitor 每 5 分钟跑一次，或在每个检查点手动跑一次。命中任一条就停这条线：

| 信号 | 判定 | 状态 |
|---|---|---|
| 碰壁 | 同一检查项连续 3 次 fail，中间没有任何新的 pass | `STALL` |
| 空转 | 超过 `--idle` 分钟（默认取上限的四分之一，最少 20 分钟）没有新的检查项转成 pass | `IDLE` |
| 到点前收口 | 用掉上限的 90%，还有检查项没过 | `WRAP` |
| 正常 | 以上都没命中 | `OK k/n` |

停的方法：Codex 线由 dex-exec.sh 的 `--max-minutes` 兜底，碰壁时 Argo 直接 `--stop`；Claude 子代理用 TaskStop。停下的线不自动重派，先走第 4 节。

## 4 升级补全，不从头再来

1. 收下做完的部分：Argo 复跑已经 pass 的检查项的验收命令，确认真的过了，diff 留在原 worktree 或存成补丁。
2. 写补全任务书：只放没过的检查项，附上它们在进度文件里的失败行、报错原文、已有 diff 路径和执行方自己的报告。下一个执行者不重读仓库、不重做已过的项。
3. 补全线上限取原上限的一半，最多 1 小时。
4. 派给升级链上高一级的型号（第 1 节），审查人仍和执行方型号不同。
5. 记账：原线的 `.meta` 补 `outcome=stalled`、`done_items=k/n`、`stall_reason=<STALL C8 fail×3 之类>`、`escalated_to=<型号/强度>`；补全线的 `.meta` 写 `escalated_from=T<n>`。

## 5 每条线都留下战绩

每次派活（Codex 线、Claude 子代理、补全线）的 `.meta` 都要有这些字段。dex-exec.sh 自动写型号、强度、起止时间、退出码；`class` 用 `--class` 传入；其余由 Argo 验收后补写（Claude 子代理的 `.meta` 整份由 Argo 手写）：

| 字段 | 取值 |
|---|---|
| `class` | 活的类别，只用这些词：取证、批量、页面实现、窄回归、跨模块、根因、性能、视觉照做、复核、审方案、补全 |
| `model`、`effort` | 实际型号和强度 |
| `outcome` | `done`（全部检查项过）、`partial`（到点、有项没过）、`stalled`（碰壁被停）、`failed`（没做成或白做） |
| `done_items` | `k/n` |
| `minutes` | 实际用时 |
| `quota_delta` | 派前派后探针读数差，例 `claude_week=+2` 或 `codex_week=+5` |
| `escalated_to`、`escalated_from`、`stall_reason` | 有升级时写 |

## 6 经验回路：所有人用同一张分工表，一起变准

主席 2026-10-14 定：大家朝一个方向走，不让每个人的派活方式各自分叉。所以起步层只有一个来源，就是 SKILL.md 第 8 节的表；这张表只随新版本更新，依据是所有回传用户的数据汇总，经主席拍板。本机的派活记录不单独改本机的起步层，只用来回传和出周报。大家按同一张表派活，回传上来的数据才能放在一起比。

1. 每场完工报告前跑 `scripts/dispatch-stats.py`，它扫本机登记过的项目（`~/.config/roadstar/projects.txt`，dex-exec.sh 每次派活自动登记；也可以用参数指定目录）里的 `docs/roadstar/**/rounds/exec-*.meta`，按「类别 × 型号 × 强度」出表：次数、完成率、碰壁率、升级率、平均用时、平均额度差。没写 `class` 的旧记录归「未分类」。完工报告的「派活经验」一节贴这张表的要点，这些数据随回传进社区汇总（`docs/社区数据回传.md`）。
2. 作者每周出一次「社区经验周报」，用社区汇总表（还没有回传数据时用作者本机的表），按下面的门槛提调整建议，交主席拍板：
   - 往下挪（省额度）：某类活在更便宜的一层有 5 次以上记录、来自至少 3 个不同的人、完成率 ≥ 90%，把这类活的起步层降到它。
   - 往上挪（少返工）：某类活在当前起步层有 5 次以上记录，完成率 < 60% 或碰壁率 > 30%，起步层升一级。
   - 样本不够的只记不改。
3. 主席点头后，改 SKILL.md 第 8 节的表和 `models.md` 的实测表，CHANGELOG 记一条，写明依据的统计行，发新版本。主席没点头的建议留在周报里，不改表。
4. 用户开场时 `scripts/update-check.py` 会提醒有没有新版本，说「更新 Roadstar」就拉到最新，分工表跟着更新。

## 7 只用 Claude 时

单家模式或主席说「这次只用 Claude」：升级链只剩 Claude 那一条，起步层同样按第 8 节表里 Claude 那一格；Haiku 能做完的不给 Sonnet，Sonnet 碰壁只把剩下的项交 Opus，Opus 碰壁才动 Fable。审查人照旧和执行方型号不同，同家复核要在纪要里写明。
