# 项目地图：新模型进项目先读的那一页

主席 2026-10-04 定的规矩：以后的项目都要模块化，做到三件事都简单：上手、修改、找 bug。地图就是为这三件事写的。Claude、Codex 或子代理进项目，先读地图就知道东西在哪、改哪里、怎么测、出了问题先看哪儿，不用翻长上下文和按日期堆起来的交接文档。

## 放在哪

`docs/模块地图.md`（英文项目用 `docs/MODULES.md`）。项目的 `CLAUDE.md` 和 `AGENTS.md` 各加一行「先读 docs/模块地图.md」，这样两家一进项目就会读到。模块自己的细节写在模块目录下的 `README.md`，地图只放指针。

## 写什么（按这个顺序）

```markdown
# <项目名> 模块地图
更新：<日期>　对应提交：<短哈希>

## 一句话
<这个项目是什么、跑在哪、给谁用。>

## 怎么跑、怎么测
- 起开发环境：<命令>
- 全量测试：<命令>（大约多久）
- 只测一个模块：见下面每块的「怎么测」
- 发布 / 安装：<命令或文档指针>

## 模块一览
| 模块 | 管什么 | 目录 |
|---|---|---|
| <名字> | <一句> | <路径> |

## 出了问题先看哪
| 症状 | 先看哪个模块 | 日志 / 排查命令 |
|---|---|---|
| <主人会怎么描述这个问题> | <模块> | <日志路径、一条命令> |

## <模块名>
- 管什么：<一两句>
- 入口：<最先该读的 2–4 个文件>
- 对外接口：<别的模块怎么用它：函数、HTTP 路由、事件、文件格式>
- 依赖：<它用到谁>；被谁用：<谁用到它>
- 怎么测：<只跑这一块的命令>
- 规矩：<改它时不能破的安全或行为约束；没有写「无」>
- 细节：<模块 README 或设计文档的路径>
```

## 写法要求

- 一个模块一节，每节不超过十行；全图控制在两三页。写不下说明模块切得太粗，拆开。
- 只写现在的样子，不写历史；历史在 CHANGELOG。
- 路径、命令必须能用：写进去之前跑一遍或至少确认文件存在。
- 「出了问题先看哪」按主席会怎么说来写症状（「微信页读不到状态」「收藏点了没反应」），不按代码里的报错名。
- 模块名在任务书、CHANGELOG、提交说明里统一用，别另起叫法。

## 谁来写、什么时候更新

- 没有地图的项目：Roadstar 开场取证前先派一件活建地图（Codex 6.1 Sol / medium 只读起草，Argo 核对路径和命令后提交），算本场第一件活。旧项目可以复盘用法里一并做。
- 每件任务书写明「涉及模块」，用地图里的名字。
- 改动碰了某个模块的入口文件、对外接口、测试命令或规矩，执行方在同一个提交里改地图那一节；验收方核对地图和代码一致，不一致算没通过。
- 新增或删掉模块，同时改「模块一览」和「出了问题先看哪」。
