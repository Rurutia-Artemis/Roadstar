## 两条注意

Fast 档按 2.5 倍扣订阅额度，圆桌脚本一律带 `--disable fast_mode`。

型号会变，缓存里有也不等于当前 CLI 能调。开场核对 `codex --version`（≥ 0.160）和 `~/.codex/models_cache.json` 的 slug 列表，和这张表不一致时在纪要里提一句；第一次用某个型号先拿 `codex exec --skip-git-repo-check -s read-only -m <型号> -c model_reasoning_effort=low --disable fast_mode --ephemeral "只回复两个字：正常"` 探一下，400 先 `codex update` 再试，还不行就换型号并记进账本。Codex 的付费 credits 余额动的是真钱，要用先有主席授权。

## 实测能力画像与「八二分」（2026-10-07/08，Mia 移动版约 25 条 Astra / Sol 线）

数据来自同一项目两天的派活记录（任务书、执行报告、Argo 复跑结果），只代表这类活（SwiftUI / iOS / Node 主机、带自动化测试的仓库），换领域要重新校准。

| 活的类型 | 第一轮能做到 | 实测例子 | 后面那段怎么办 |
|---|---|---|---|
| 规格写死的功能实现、照样张做页面、补测试、合并冲突 | 九成以上一次过，测试自己补齐，报告诚实（没达标会写没达标） | 十一条移动版首批线各约 40 分钟完成；T74 照样张做首页 / 用量页 / 七种环，两组 29 个用例全过；T71 合并冲突加全页面排查 96/96 | 剩下的多是整合问题（跨线命名撞车、登记文件），Argo 合并时手修，几十行以内 |
| 有明确症状的 bug 查根因 | 能查到根，但要给它真实证据和能复现的环境 | T67 定位「全屏点不动」是状态刷新死循环；T71 定位 Tailscale 被 iOS ATS 拦；T77 把公众号文章问题的两段根因都找到了 | 给它日志、会话记录、数据库只读副本；症状描述太窄时它只修症状（文章问题前两次就是这样），任务书要写「先排时间线、再找根因」 |
| 视觉设计、审美判断 | 基本不行 | 首页、额度页、设置图标连着被主席判「丑」「不高级」 | Argo 出样张，主席点头后 Codex 照做 |
| 开放式优化（性能、体验）对着严格数字 | 前几轮能拿到大头，之后在细小数字上反复试、不会自己回头质疑标准或环境 | T75 跑七个半小时、约三成周额度：持续输出 CPU 约 20%→8%、键条响应 0.16s→0.01s、卡死清零，但在模拟器上追「16ms」「滑动长帧 2 次」一直不收敛 | 设时间上限和检查点；不收敛就停，Argo 判断剩下的是真问题还是测法问题，真问题由 Argo 查清根因写方案，Codex 只实现 |

由此定的分工（省额度的做法）：

- **八成交 Codex**：规格清楚的实现、批量修改、测试、取证、按方案落地。每件给能失败的完成线和时间上限。
- **两成 Argo 自己做或走 Claude 梯子**：定标准和样张；两轮不收敛时的根因诊断与方案；合并后的整合小修（几十行以内、改哪一处已经清楚的）；发版前在合并后的主干复跑。剩下那两成如果是「已经定位到一处、改动很小」的缺陷，Argo 直接改比再派一轮便宜；如果还没定位，先拿真实环境的证据（真机 trace、线上日志），没证据不动手。
- 不知道剩下的两成是不是真问题时（比如只在模拟器上不达标），先拿到真实环境的判断，再决定修不修。
