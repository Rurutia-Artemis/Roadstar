# Roadstar · 引路星：先选模型，再谈、再派、再审

探讨：主席只说构思，两家围着同一份 `plan.md` 谈到能落地。复盘：两家各读一遍现有项目，交叉审出不足和先做的三件事。协同：方案已有，派活、验收、交报告。不管哪种，开始前先选模型，派活前先看推荐。

## 谁是谁

| 标签 | 是谁 | 怎么参与 |
|---|---|---|
| 主席 | 用户 | 定目标与约束，开场定这次模型怎么用，随时插话，对争议拍板 |
| Argo | Claude Code 主会话（Fable 5.1 或 Opus 5.5，账本记实际模型） | 主持、起草改稿、记账、调度、验收裁定、汇报 |
| Dex | Codex CLI（`codex exec`，走 ChatGPT 订阅） | 每轮按契约审稿；执行分给它的任务；复核对方的活。型号按任务选：Astra 最强、6.1 Sol 常规（6.1 Sol 要 codex-cli 0.160 以上）；Luna 不派活 |
| Pro | 网页 GPT Pro（可选） | 大活起草或终审；Codex 空时的跨家审稿兜底；每趟要主席动手 |

型号、用途、强度见 `references/models.md`。名字只是发言标签，没有人设。Argo 转述 Dex 时原文照贴进账本、标明 `Dex：`，自己的回应另起一段；主席的话记进账本，效力最高。改名只改这张表。

## 三种用法

探讨（「探讨一下怎么落地」「开圆桌」）：主席只有构思，或要做新项目、大改动、难回滚的事。§0 到 §5（纪要带推荐分工表）→ 主席说开工 → §8。模型默认最强（总调度 Fable 或 Opus，审稿 Astra / high，大活加网页 Pro），主席可改。

复盘（「复盘这个项目」「看看哪里能改进」）：现有项目，主席想知道哪里不足、先改什么。§0 → §1（brief 写尺子：以什么为标准）→ 两家各自只读取证、各出不足清单 → Argo 合并 → §3 审合并稿（熔断 3）→ §5 纪要：不足清单按严重度 + 先做的三件事 + 推荐分工表 → 主席选哪几件 → §8。

协同（「直接调度」「你来安排谁做」「总舵主」）：方案已有（Plan 模式产出、别处的方案、探讨或复盘的结论），且不止一件能独立验收的活。§0 → §8 推荐 → 主席定 → §9 → 完工报告。细节见 `references/modes.md`。

一小时内能做完的活直接干；只要一次第二意见走 call-codex；只要 Pro 策划走 pro-orchestrator。

好处有两条。两家模型的盲区不重合，交叉审稿能抓到自审抓不到的漏洞；账本和清单把「想到哪说到哪」变成写下来、逐条清零的过程，方案完整靠制度而非记性。实现统一交 Codex，Claude 额度留给主会话调度、任务书和验收。代价是两边的订阅额度和时间。

## 流程

### 0 选模型（三种用法都从这里开始，主席答了才往下）

1. 跑 `scripts/quota-status.py` 和 `codex --version`，列当下能用的模型和读数：Claude 的 Fable 5.1 / Opus 5.5 / Sonnet 5.5（标出主会话是哪个，5 小时和周额度，Fable 单列）；Codex 的 `gpt-6-astra` / `gpt-6.1-sol`（周额度、重置卡数），Luna 列出标「不推荐」。
2. 用 AskUserQuestion 一次问三件，每件先给推荐和一句理由，选项能一个字答：
   - 总调度用哪个：现在的不换 / 换 Opus 5.5 / 换 Fable 5.1（要主席敲 `/model`，我说一句怎么敲）。
   - 探讨和审稿用哪个：Astra / high（推荐）/ Astra / xhigh / 6.1 Sol / high / 加网页 Pro 终审。
   - 执行怎么分：按我每件推荐（推荐，难 Astra、常规 6.1 Sol）/ 逐件指定 Codex 型号和强度。想逐件点的主席在第 5 段的推荐表上点，每问最多四个选项，工具自带「其他」。
3. 答复记进账本「主席指令」，管整场；中途改就改账本。主席说「你定」才按 `references/division-of-labor.md` 的表自动排。问完之前不取证、不起草、不派活。

### 1 立项

主席一句话说目标，Argo 写 `brief.md`。目标和约束够写出验收标准就直接起草，不等点头，brief 里的假设在纪要里列给主席；只有缺口会改变结果时才问，一次问齐，最多三个。brief 必填：目标、非目标、硬约束、规模（小 / 中 / 大）、参与配置。参与配置五项 Argo 填默认值，主席随时改：

- 模型用法。抄第 0 节主席选的结果。
- 审稿模型与强度。写死型号，默认 `gpt-6-astra` / high；规模大或难回滚用 xhigh；Codex 紧时 `gpt-6.1-sol` / high。一场不换审稿人。
- Pro 参不参与。规模「大」默认起草 + 终审；「中」默认只终审；「小」默认不参与。
- 节奏。默认连跑：内环一口气跑到停机条件，中间不向主席开口。主席说「每轮停一下」才逐轮。
- 熔断轮数。默认 6，Codex 紧时 3，到顶把取舍类未决项交主席，不算失败。

开场只回一句，格式固定：「开始了：<用法>，题目：<一句人话>。模型按你选的：总调度 X，审稿 Y，执行 Z。跑到有结果再来找你。」有要问的就把问题接在这句后面，一次问齐。此后到停机为止不再开口。brief 之后主席改目标或约束，记进账本「主席指令」，两边下一轮都读到。

### 2 起草

取证从项目地图开始：先读 `docs/模块地图.md`（规格见 `references/project-map.md`）。没有地图或地图和代码对不上，先派一件活建或补地图（Codex 6.1 Sol / medium 只读起草，Argo 核对路径和命令能用后提交），算本场第一件活。其余取证只补地图没写的。

取证（读代码、跑只读命令、查文档）在起草前一次做完，派给 Codex 6.1 Sol / low 或 medium 只读，一次发出、一次收齐；结果只进 plan 的「现状」，主会话只收结论、不读大段代码，也不分批向主席回报。

规模小、中：Argo 起草 `plan.md`，按 plan-template 的必填槽位写满，写不出的槽位标「待定 + 缺什么信息」。

规模大且 Pro 参与：先让 Pro 起草（见 `references/pro-stage.md`），Argo 把 Pro 稿整理进 `plan.md` 后，第一轮 Argo 和 Dex 各审一遍，两边的议题一起进账本。审别人的稿比审自己的狠，这是让 Pro 起草的主要收益。

### 3 内环，每轮这样跑

1. 快照并送审：`scripts/dex-review.sh <plan-dir> --model <型号> --effort <强度>`，型号和强度取自 brief。第一轮把审稿契约、brief、plan 全文、账本和主席问 Dex 的话拼成请求；第二轮起默认精简，只发 diff、账本里没解决的和上轮刚解决的议题，plan 全文只给路径让 Dex 按需读，`--full` 可切回全发。跑 `codex exec` 拿结构化 JSON。
2. 渲染：`scripts/render-review.py rounds/rN-dex-review.json` 转成可读文本，抄进账本；主席不在内环里看到它。
3. Argo 逐条处置 Dex 的议题：接受就改 plan 并在账本记「已解决（rN）+ 改了哪」；拒绝要写理由和证据；拿不准的标「问主席」。Dex 给了可复现的反例（命令、行号、输出），先在本机复现再改；改出来的判定规则用同一批反例跑一遍再记已解决，凭记忆写的规则会被连判两轮无效。同一条议题第二次被拒，或 Dex 第二次判 Argo 的解决无效，自动变「争议」。范围外的建议进停车场，主席定去留。
4. Argo 也审 Dex：Dex 提出的替代方案和补充，Argo 按同一清单回评，不是照单全收。
5. 更新账本状态行，按第 4 节判停；没停就直接进下一轮，不向主席开口。
6. 主席插话（任何时候）：指令记进「主席指令」；主席直接问 Dex 的话写进 `rounds/r(N+1)-chair-to-dex.md`，下一轮原样带给 Dex，Dex 在 `reply_to_chair` 里答，答复进下一份纪要。

Dex 的「同意」不算数：PASS 必须清单逐项打勾且零阻塞项；阻塞项必须带证据（文件位置、命令输出或文档）。从第二轮起 Dex 只审 diff 和开放议题，不重翻已定项，除非能证明结论是错的。

### 4 什么时候停

停机看账本，不看轮数。每轮处置完，Argo 按下面顺序判断，命中一条就停：

| 条件 | 判定 | 动作 |
|---|---|---|
| 争议 | 账本里有「争议」或「问主席」未清 | 事实类 Argo 取证了结、账本记证据支持谁，不用停；取舍类停下来，列双方理由请主席裁决（分类见 ledger-format） |
| 收敛 | 本轮零新阻塞项，开放阻塞项为零，且 Argo 处置后 plan 无实质改动（`rN-plan.diff` 为空或只有措辞） | 定稿候选 |
| 只剩小意见 | 开放项和本轮新项都只有「小意见」 | 定稿候选，小意见列在 plan 末尾当可选项 |
| 主席说停 | 任何时候 | 按主席说的办，账本记「主席终止」 |
| 熔断 | 轮次到 brief 里的上限 | 停。事实类未决项 Argo 自己用证据了结，只把取舍类交主席；不自动定稿 |

都没命中直接进下一轮。命中任何一条 Argo 才开口，开口只交纪要。

### 5 纪要：内环静默，停机才开口，写给不看代码的人

内环期间不播报进度，过程只落到文件和账本；系统催促回话时只回一行「圆桌进行中，第 N 轮」。

命中停机条件后 Argo 交一份纪要，这是主席看到的全部，按下面的顺序写，模板与例子见 `references/minutes-template.md`：

1. 结果一句：定了可以开工 / 还差一件事 / 卡住了要你选。
2. 商量出来的方案：三到五句大白话，讲清做成什么样、怎么做、怎么算做完。
3. 讨论改了什么：只挑影响结果的，最多三条，句式「原来打算…，Codex 指出…，改成…」；其余一句带过（「另外还修了七处细节」）。
4. 你要做的：第一条固定是第 5 段表后那一问。其余每件一句，先给选项再给建议，能一个字答。只问主席能判断的事：做不做、花多少、要什么舍什么；技术细节 Argo 自己定，纪要里一句带过。
5. 推荐分工表：每件活一行，人话任务名 / 推荐给谁（型号·强度）/ 一句理由 / 备选 / 大概多久；表前一句说按主席选的方向排的，表后问「按推荐来，还是改哪几条？（例：第 3 件换 Codex 的 Astra）」。称呼按 minutes-template 写。主席答了才派活，答复记账本。
6. 细节在哪：一行路径。

硬规矩：纪要里 Argo 自称「我」，Dex 写「Codex」，Pro 写「网页 Pro」；代号、命令、工具名不进纪要；写完按 minutes-template 的写法要求自检。逐轮模式的每轮汇报同一配方。

### 6 定稿，可以开工的门槛

同时满足才算定稿：账本无争议、无待答问题；plan 必填槽位全部有内容且验收标准可判定；命中「收敛」或「只剩小意见」；Pro 终审（若参与）的阻塞项已清；主席说「定稿」。Argo 在 plan 顶部写 `状态：定稿 <日期>`，账本写终态计数。

### 7 终审（Pro 参与时）

定稿候选交 Pro 看一遍，只收阻塞项和建议项，进账本走同一套处置。通道和请求模板见 `references/pro-stage.md`。Pro 提的争议同样交主席。

### 8 调度

派活前再跑一次 `scripts/quota-status.py`。每件活判四点：难度、验收条件、执行环境、上下文，判法见 division-of-labor 第 5 节。多条命中按顺序取第一条：主席的硬话 > 执行环境 > 验收条件 > 难度 > 额度方向。再查 `references/division-of-labor.md` 的表，在主席定的方向里挑型号和强度。

拆线按文件归属：共享中枢（登记表、路由、大 Store）只归一条线，其它线走扩展点或串行；要模拟器的线同时最多两条。推荐写进 plan §10 分工表（列头见 plan-template）。需要浏览器或模拟器核验的活，由 Claude 主会话自己做，或交 Codex，不再派 Claude 子代理。

推荐表给主席看，主席定了才派；主席逐件点的照点，说按推荐的照推荐；不照表推荐要在理由栏写一句。主席的硬话入账本，压过额度；硬话和额度撞上时在纪要里报一句冲突，不默默照做也不默默降级。

### 9 执行与验收

- 每件活一份任务书（`references/task-brief-template.md`），派给谁都能做。**一份任务书一个目标、一条能失败的完成线**；独立的事超过三件就拆成多份并行。派之前过一遍 division-of-labor 第 15 节（两天实战踩过的坑与做法）。
- 任务书写明涉及哪几个模块（用地图里的名字）。改动碰了模块的入口文件、对外接口、测试命令或规矩，执行方在同一提交里更新地图那一节；验收方核对地图和代码一致，不一致算没通过。
- Codex 任务：`scripts/dex-exec.sh <plan-dir> T<n> --model … --effort … --brief …`，默认只读，要改文件加 `--write`；脚本显式传 `-s`、`-m`、`-c model_reasoning_effort=`、`--disable fast_mode`，不派 Claude 子代理。长任务、返工、并行 worktree 与合并见 division-of-labor 第 9 节。
- 验收分级与配对见 division-of-labor 第 8 节：中和难的由 Claude 主会话自己跑命令核对，或另开 Codex 只读会话复核；钱、权限、迁移类由 Claude 主会话核验 Codex 的实现，不接受执行会话自验或仅同家复核。验收标准来自 plan，不临时降标，证据写进 §11。
- 失败上限和额度到顶的梯子见 division-of-labor 第 10、11 节；每次改派、挂起和成本（派活前后的读数差）都记进调度记录，完工报告写一行。
- 发版或交付前，Argo 在合并后的主干上亲自复跑至少一组完整验收（不只信执行方的数字）；合并后把该线 worktree 挪进废纸篓，自建模拟器删掉，查一眼同机生产服务还活着。
- 执行期静默；全部通过后在 plan 追加执行记录、写共享记忆、交完工报告（配方见 minutes-template 末尾）。

## 纪律

- 主席开口的点固定：开头选模型、看推荐表定分工、中途拍板争议、最后收报告；其余时间静默，被系统催促只回一行。
- 主会话只产出四样：brief、plan 改稿、任务书、裁定。Argo 自己打开源文件改代码，就等于漏写了一份任务书。
- 转述不加工：阻塞和争议项贴 Dex、Pro 的原话并标明谁说的，贴进账本，其余给要点；Argo 的判断另写。软化对方的批评等于篡改账本。
- 证据先于立场：阻塞项要证据，拒绝要理由；事实类争议 Argo 取证了结，取舍类交主席。
- 项目要模块化：上手、修改、找 bug 都从地图出发；地图跟着代码改，过期的地图比没有更坏。
- 范围不悄悄涨：范围外建议一律进停车场。
- 密钥不进 prompt：喂给 Dex 和 Pro 的内容等于发给外部服务。
- 默认不加 `--dangerously-*`；审稿和复核用 `-s read-only`，执行用 `--write`。例外只有一种：验收必须起模拟器、开端口、真点界面而沙箱做不到时，用 `-s danger-full-access`，任务书写死边界块（只改本 worktree、临时端口、自建模拟器、不碰生产与用户数据、`HISTFILE=/dev/null`、不提交），见 division-of-labor 第 15 节。真动工作区外的那一步（/Applications、LaunchAgent、Obsidian、生产）仍由 Argo 或主席做。
- 账本是唯一真相：主席的裁决、双方的让步都要落到 ledger.md，调度记录也在账本，聊天里说过不算。
